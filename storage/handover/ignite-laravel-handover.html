Technical Handover

Ignite Talent Group
Static Site → Laravel Port

What was built, how it maps to the original site, and how to deploy it on AWS EC2.

Prepared 8 October 2026 · Laravel 11 · PHP 8.2+ · Server-rendered Blade

1. Overview

The original Ignite Talent Group website was a static front end (HTML, CSS and a single app.js that built every page in the browser). It has been ported to a server-rendered Laravel application so pages render on the server, content is driven from one config file, and the contact and testimonial forms are backed by a real database and a moderation workflow — the production flow the original README set out as the next step.

All approved marketing copy, company details, policy documents and sector branding were preserved exactly. Nothing in the public-facing content was invented or changed.

3. What was built this phase

Public site

  • Landing brand chooser (/), group overview (/group), and the five sector pages.
  • Construction uses the canonical URL /construction; the legacy /construction.html and /construction/index.html paths 301-redirect to it.
  • Construction compliance / policy hub at /construction/policies with all controlled PDFs.
  • Per-sector testimonials pages and a review submission form (gated — see §7).

Forms & data

  • Contact form stores a ContactMessage and emails the Ignite inbox. Includes a honeypot anti-spam field and server-side validation.
  • Testimonial submissions are stored as pending and never shown publicly until approved.

Admin area (/admin, login required)

  • Dashboard with counts of pending reviews and unhandled messages.
  • Testimonial moderation: approve, reject/unpublish, delete.
  • Contact message inbox with a handled / new toggle.
  • Access is restricted by the admin middleware (EnsureUserIsAdmin) — only users flagged is_admin can enter.

Database tables

  • users (with is_admin), plus framework tables (sessions, cache, jobs).
  • testimonials — sector, author, rating, body, status, moderation fields.
  • contact_messages — sector, name, email, message, handled timestamp.

5. Prerequisites on the server

  • PHP 8.2+ with extensions: pdo, mbstring, openssl, ctype, tokenizer, xml, curl, and the driver for your database (pdo_mysql for RDS).
  • Composer.
  • A web server (Nginx or Apache) with the document root pointed at public/.
  • Access to the AWS RDS MySQL database and, for email, AWS SES.
Note on local build. Dependencies were not installed in the authoring environment because its network proxy intercepts TLS in a way PHP’s OpenSSL rejects (curl error 60). This is environment-specific and does not occur on a normal EC2 host. All PHP files were syntax-checked and all view routes were verified instead.

6. Deployment on AWS EC2

Step 1 — Get the code onto the instance

git clone <your-repo> /var/www/ignite
cd /var/www/ignite
composer install --no-dev --optimize-autoloader

Step 2 — Configure environment

cp .env.example .env
php artisan key:generate

Then edit .env:

APP_ENV=production
APP_DEBUG=false
APP_URL=https://ignitetalentgroup.co.uk

DB_CONNECTION=mysql
DB_HOST=<your-rds-endpoint>
DB_PORT=3306
DB_DATABASE=<database>
DB_USERNAME=<user>
DB_PASSWORD=<password>

MAIL_MAILER=ses
AWS_DEFAULT_REGION=eu-west-2
IGNITE_CONTACT_EMAIL=info@ignitetalentgroup.co.uk

# First admin account (used once by the seeder)
ADMIN_EMAIL=you@ignitetalentgroup.co.uk
ADMIN_PASSWORD=<a-strong-password>

# Keep the public review form closed until you are ready
IGNITE_REVIEWS_OPEN=false

Step 3 — Database

php artisan migrate --force
php artisan db:seed --force   # creates the admin user from the env values above
Review the existing WordPress RDS database first. Per the original handover, an existing MySQL database may already be on RDS. Reconcile these tables with any existing data (or point the app at a fresh schema) rather than assuming an empty database.

Step 4 — Permissions & caching

chown -R www-data:www-data storage bootstrap/cache
php artisan config:cache
php artisan route:cache
php artisan view:cache

Step 5 — Web server (Nginx example)

server {
    listen 80;
    server_name ignitetalentgroup.co.uk;
    root /var/www/ignite/public;      # document root MUST be public/

    index index.php;
    location / { try_files $uri $uri/ /index.php?$query_string; }
    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        include fastcgi_params;
    }
    location ~ /\.(?!well-known).* { deny all; }
}

Step 6 — HTTPS & security headers

  • Terminate TLS at the load balancer (ACM certificate) or use Certbot on the instance. HTTPS is required for production.
  • Re-apply the original security headers (the static site shipped these in _headers): X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy: camera=(), microphone=(), geolocation=().

7. Operating the site

  • Admin login: /login → /admin. Sign in with the seeded admin account.
  • Opening reviews: set IGNITE_REVIEWS_OPEN=true and re-run php artisan config:cache. Submissions then arrive as pending and must be approved in the admin area before they appear publicly.
  • Contact messages: every submission is stored and emailed to IGNITE_CONTACT_EMAIL; triage them under Admin → Messages.
  • Updating a policy PDF: replace the file in public/documents/policies/ keeping the same filename — no code change needed.
